# Androidでのプツ音の検証

[English](ANDROID_TEST_EN.md) | [日本語](ANDROID_TEST.md)

## USBパケット記録の実験

UAC1の診断ビルドを `USB_BRINGUP_LEVEL=3`、`USB_AUDIO_CLASS_VERSION=1`、
`USB_PACKET_TRACE_ENABLE=ON` で構成します。このオプションは既定ではOFFです。
通常版には記録処理も画面も追加されません。リポジトリ同梱のTinyUSBが必要です。
UAC2の診断ビルドでも使用できます。

1. Androidを接続したまま、同じ音源を対象ドライバーで再生します。電源投入後、
   最初の音声OUT転送完了から最大1024件をRAMに記録します。コールバック内では印字しません。
2. Xで `USB PACKET TRACE` 画面に切り替え、A/Bで12件ずつ前後に移動して撮影します。
   `INDEX`は0始まりの受信順、`TIME_US`は先頭の転送完了処理からの経過マイクロ秒、
   `BYTES`は受信長、`EP`は16進エンドポイント、`ALT`はalternate settingです。
   `RATE`は最初の受信時の要求レート、ビット数と1サンプル当たりのバイト数は
   最初のALTの記述子に対応します。UAC1はALT 1が16bit・2バイト、ALT 2が24bit・3バイトです。
3. `ARMED`は受信待ち、`RECORDING`は記録中、`SAVED`は記録停止済みです。
   1024件で上書きせず停止し、それ以前にストリームが終了するかレート・ALTが変わった場合は、
   それまでの件数で停止します。再接続や別の再生では消去されません。
4. 再試行する場合は再生を停止し、診断画面でYを3秒長押しして再武装してから再生します。
   これはパケット記録だけでなく既存の診断カウンター・イベントもリセットします。
   再生中に再武装すると、その時点の次のパケットから記録します。
   各ドライバーで同じ手順を使い、画面を撮影してください。

この記録は約8KBの揮発性RAMを使います。給電が途切れると消えるため、Android接続中に撮影してください。
最初の1024件は1msごとのパケットなら約1秒分で、後から発生するプツ音は含まれません。
記録はTinyUSBに通知された転送完了が対象で、ホストが送信しなかったパケットや通知されない転送は含まれません。
時刻はUSBバス上の到着時刻ではなくTinyUSBの転送完了処理時刻であり、
タスク処理遅延の影響を受けます。32bit時刻の差は約71.6分を周期として計算します。
画面描画とRAM記録は負荷を追加するため、症状への影響は実機で確認してください。

2026年11月21日のAndroid再生試行では、48kHz・24bit、EP `01`、ALT `2`で1024件の記録完了を画面で確認し、試行中にノイズは聞こえませんでした。画面に表示されたINDEX 36〜47は288バイトまたは294バイトでした。これは一度の観察であり、長時間の安定性や従来のノイズが解消したことを示すものではありません。

## 過去の検証記録

本プロジェクトでも同様のプツ音が発生し、以前はフィードバック制限値を`FB_BASE_LIMIT_PPM=50`、`FB_BOOST_MAX_PPM=500`に変更しました。以下は派生版の[Pico2_UAC12_USBDDC_Weather](https://github.com/Toshimiyu/Pico2_UAC12_USBDDC_Weather)での過去の検証結果であり、本プロジェクトの現在の設定での測定値ではありません。Foobar2000 Android版の記録はV2.1より前の参考情報で、現在のサポート対象を示すものではありません。

2026年11月13日、Sony XQ-ES44（Android 16、標準オーディオドライバー）をUAC2で使用し、48kHz / 32bitで再生した際の観察結果です。Windows 11 26H2でも48kHz / 32bitで比較しました。

- AndroidのYouTubeとMusicアプリでは、不定期に短いプツ音が発生しました。水位が約50%で安定した後にも発生し、Androidの音量を変更してもプツ音の大きさは変わりませんでした。
- Androidで無音WAVを再生した際には、プツ音は確認されませんでした。無音再生時のUSB形式は未確認です。
- `FB_BASE_LIMIT_PPM=50`、`FB_BOOST_MAX_PPM=500`の試験設定では、Windowsで水位が約3分40秒後に49.9%となり、音切れは確認されませんでした。V2.1より前のAndroid版Foobar2000の参考検証では水位が約2分27秒後に50%となり、プツ音は確認されませんでした。同設定のMusicアプリではプツ音が残りました。
- MusicアプリでDSEE UltimateをOFFにすると、プツ音の頻度はかなり下がりましたが、不定期のプツ音と一瞬音が濁るような現象は残りました。
- 診断画面ではO/F/S/C/Uが0で、異常イベントは確認されませんでした。これは全ての音声異常がないことを保証するものではありません。

フィードバック制限値を小さくすると改善する傾向がありましたが、原因は未特定です。アプリや音響効果、フィードバック制御との関係を引き続き確認する必要があります。Foobar2000 Android版の記録はV2.1以前の参考検証であり、現在のサポート対象ではありません。DSEE Ultimateの無効化も当時の回避策の候補にとどまります。V2.2でOutput Terminalを`0x0301`へ変更した後、UAC1モードでAndroid標準ドライバーによる認識と、Onkyo HF Playerでの再生を実機確認しました。標準ドライバーでの再生時に発生するノイズは調査中で、長時間の安定性も未確認です。Onkyo HF PlayerのUSBドライバーを使用したUAC1動作も実機確認済みです。補正幅を小さくしすぎると水位が漂い、音切れする可能性があります。

#### 今回の調整後の状況

- 容量・目標水位・フィードバックなどの調整後、水位の大きな落ち込みはほぼ見られなくなりましたが、まれにプツ音が残っています。複数の設定を変更したため、個々の変更の効果は分離できていません。
- UAC1のフィードバックはTinyUSB内で10.14形式に変換して送信します。UAC1の音量`SET_RES`拒否は診断ログで確認し、対応しました。
- 同系統のレート切替ではPLLの再設定を省略しますが、PIOは停止・再初期化されます。出力開始時にもPIOを再初期化します。
- 調整後のプツ音の頻度比較、OVERFLOW / UNDERFLOWの発生状況、およびフィードバック補正が上限に張り付くかは未確認です。
- ノイズ発生時のBCLK・LRCK・DATAとDACアナログ出力の波形は未測定で、原因がホスト側・デバイス側・DAC側のどこにあるかは特定できていません。将来は録音、信号の同時観測、別端末での比較が切り分けの候補です。

#### 2026年11月19日時点の整理と検証方針

##### 確認できている事実・観察

- 同じHF Player・同じ音源での比較では、Android標準ドライバー使用時にプツ音があり、HF Player USB Driver使用時には確認されていません。試行回数や発生頻度の定量値は未記録です。
- V2.2ではプツ音がかなり減ったという聴感上の印象がありますが、定量比較はしていません。
- V2.2ではフィードバック制御を含む複数の変更が行われており、各変更の効果は分離されていません。明確なUNDERFLOWなどの診断記録がないことだけでは、プツ音がなかったとは判断できません。
- 最終的なV2.2の目標水位はリング容量4096フレームの50%に当たる2048フレームです。2150フレームはClaudeが試験用に提示した値であり、ユーザーが設計値として指定したものではありません。2150から2048への変更が改善に寄与したという根拠はありません。
- TinyUSB Discussion #4547は回答待ちです。

##### 仮説（未確認）

- ホスト・デバイス双方が仕様上動作していても、Feedbackの変化や応答とバッファー制御の組み合わせにより、特定のホストとデバイス間で相互運用性の問題が現れる可能性があります。
- V2.2の制御変更によって瞬間的な揺らぎへの追従が穏やかになり、結果として症状が軽減した可能性はあります。一方、PI制御との関係や改善理由を裏付ける測定結果はまだありません。
- 現時点では、ホスト側またはデバイス側の一方を原因と断定せず、改善理由も未確定として扱います。

##### 「歩み寄り」を検証する測定項目

可能な限り同じ端末・接続・HF Player・音源・サンプルレート・ビット深度・音量・音響効果・再生時間で、Android標準ドライバーとHF Player USB Driverを複数回比較します。各試行でファームウェア版、ビルド設定、ドライバー、条件、試行時間を記録し、プツ音の発生時刻と回数を記録音と対応付けます。

- **音声症状:** 発生回数・時刻、録音波形、可能ならDACアナログ出力とBCLK / LRCK / DATAの同時観測。デジタル側に異常が見えない場合も、聴感上の症状がないとは限りません。
- **バッファーと異常:** `RING_NOW` / `RING_MIN` / `RING_AVG` / `RING_MAX`、UNDERFLOW、OVERFLOW、無音DMA補完の有無と発生時刻。
- **Feedback制御:** `FEEDBACK_RATE`、`HOST_RATE`、`HF_DIFF_NOW`、`FB_LEVEL`、`FB_INTEG_HZ`に加え、取得可能な場合は`FB_CORR_PPM_X10`、`FB_LIMIT_PPM_X10`、`FB_OUT_SAT`、`FB_I_SAT`を試行ごとに比較します。CDCログは診断負荷になる可能性があるため、CDC有効・無効で症状が変わらないかも確認します。
- **USB受信状況:** `USB_OUT_AGE_US`、`USB_GAP_MAX_US`、受信間隔と症状発生時刻の関係。これらの値だけでホスト側の原因とは断定しません。

##### 対策案の切り分け

- **ホスト側:** ドライバー、アプリ、音響効果、要求フォーマットを記録し、取得可能ならUSBトレースやホスト側ログでFeedbackの受信・適用状況を確認します。Android標準ドライバーの実装変更は本デバイス側から制御できないため、観測結果を添えて関係する実装者へ相談します。
- **デバイス側:** 目標水位だけでなく、PI制御、Anti-Windup、レート比例ゲイン、クロック差推定値の引き継ぎなどを一度に一要素ずつ比較します。水位、補正の変動・飽和、音切れも併せて評価し、プツ音だけを減らしてアンダーフロー余裕を損なわないことを確認します。

これらは今後の検証案であり、現時点でホストとデバイスのどちらかに規格違反があることや、特定の対策が有効であることを示すものではありません。
